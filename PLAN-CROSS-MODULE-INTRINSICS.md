# Cross-Module Template Intrinsic Support — Implementation Plan

## Goal

Enable `UniSlot<T>` (and future intrinsic templates like `MultiSlot<T>`) to be
used across module boundaries: a consumer module that `import k;` can instantiate
`UniSlot<MyType>` and have its intrinsic methods (`construct`, `destruct`, etc.)
work correctly.

---

## Current State

### What works today (cross-module templates)

- Consumer-side instantiation of imported template structs with regular method bodies ✅
- Consumer-side instantiation of imported template functions ✅
- Template source text capture and re-parse across KDI boundary ✅
- Value template parameters across import boundary ✅

### What doesn't work (the gap)

When a template struct has `@Intrinsic`-annotated methods (methods WITHOUT a body,
whose IR is generated by the compiler):

1. The `k_source_emitter` does NOT emit annotations on functions → the re-emitted
   source text loses `@annotations::Intrinsic("UniSlot::construct")`.
2. Even if annotations were preserved, the `k_source_emitter::emit_function` emits
   bodyless functions as just `name(params) : ret;` — the parser may reject them or
   the model_builder may flag them as errors.
3. The member template syntax (`template<typename...Args> construct(Args...args)`)
   is not handled by `emit_function` — no template clause is emitted for member
   templates.

---

## Root Cause Analysis

The pipeline for cross-module template instantiation is:

```
[Export side]
  memory.k parsed → model UniSlot<T> built → kdi_exporter
    → tries k_source_emitter::emit_template_aggregate()
    → if that fails/is empty: uses tpl_info.source_text (raw parse-time capture)
    → writes to .kdi file as kdi_template_def.source

[Import side]
  consumer does `import k;` → kdi_importer::materialise_template_def()
    → wraps source in `module k;\n<source>`
    → re-parses as a fresh AST unit
    → model_builder builds template aggregate into consumer's model
    → consumer uses UniSlot<MyType> → template instantiation triggered
    → instantiated methods go through resolution → codegen
    → implementation_generator::visit_function → intrinsic dispatch
```

**Problem A**: The `source_text` path should work since it captures the raw source
from the original `.k` file. Let's verify by checking what `tpl_info.source_text`
contains for UniSlot.

**Problem B**: Even with source_text correctly propagated, the importing compiler
must have the `@annotations::Intrinsic` annotation type available in its model to
resolve the annotation. Since `import k;` is auto-injected for all modules except
`k` itself, and the Intrinsic annotation is in `k::annotations`, it should be
available.

**Problem C**: The consumer's `@Intrinsic` annotation on the re-parsed template
methods must survive through template instantiation (already done — Phase 6 of
UniSlot copies annotations during instantiation).

## Investigation Steps (must be verified before coding)

### Step 0: Verify source_text capture

**Question**: Does the parser correctly capture `template_source_text` for
UniSlot in `memory.k`?

**How to check**: The capture happens in `parser_declarations.cpp:913-917`.
It captures from `tpl_kw_start` (the 'template' keyword position) through
the closing `}`. Since UniSlot now has a member template (`template<typename...Args>
construct(...)`), the `tpl_kw_start` should point to the OUTER `template<typename T>`.

**Risk**: The parser's `tpl_kw_start` might not correctly point to the start of
the outer template clause if inner template methods confuse the detection.

**Test**: Add a unit test that compiles `memory.k`, exports the KDI, reads back
the `kdi_template_def.source` field, and verifies it contains the full UniSlot
source including annotations.

### Step 1: Verify the re-parse path works end-to-end

**Question**: Does `materialise_template_def` successfully re-parse and build
UniSlot from its captured source_text?

**How to check**: Write a test using `build_exec_with_lib`:
- Library: defines UniSlot<T> with @Intrinsic annotations (inline, not from libk)
- Consumer: instantiates UniSlot<int>, calls construct(), get(), destruct()

**Expected failure mode**: Either a parse error (syntax not handled during
re-parse) or a resolution error (@Intrinsic annotation type not found).

### Step 2: Verify intrinsic dispatch on re-parsed template instantiation

**Question**: When the consumer instantiates UniSlot<int> from the imported
template definition, does `get_intrinsic_name()` correctly detect the intrinsic
on the instantiated methods?

**How to check**: Step 1's test will reveal this. If Step 1 passes parsing
but the intrinsic isn't detected, it means annotations aren't preserved through
the import→instantiate pipeline.

## Implementation Steps

### Phase 1: k_source_emitter — emit annotations on functions

**File**: `klang/src/model/tools/k_source_emitter.cpp`

The `emit_function()` method must emit annotation definitions before the function
signature. Add:

```cpp
void k_source_emitter::emit_function(const function& fn) {
    // NEW: emit annotations
    for (auto& ann : fn.get_annotations()) {
        emit_annotation_instance(ann);
    }
    // ... existing visibility, specifiers, name, params, return type ...
}
```

Need to implement `emit_annotation_instance()` that outputs:
- `@annotations::Intrinsic("UniSlot::construct")` — for string-arg annotations
- `@Name(args...)` — general form

Similarly for `emit_constructor()` and `emit_destructor()`.

### Phase 2: k_source_emitter — emit member template clause

**File**: `klang/src/model/tools/k_source_emitter.cpp`

The `emit_function()` method must detect if the function has its own `tpl_info`
(is a member template) and emit the template clause before the function name:

```cpp
void k_source_emitter::emit_function(const function& fn) {
    // ...annotations...
    // NEW: member template clause
    if (fn.get_tpl_info()) {
        emit_template_clause(*fn.get_tpl_info());
    }
    // ...existing code...
}
```

Also need to handle pack parameters in `emit_parameter_list()` — if a parameter
is a pack expansion, emit `Args...args` syntax.

### Phase 3: k_source_emitter — handle bodyless intrinsic functions

**File**: `klang/src/model/tools/k_source_emitter.cpp`

Currently, if a function has no block, `emit_function` outputs `name(params);`.
This is fine — the K parser accepts bodyless declarations inside structs.
But verify that the re-parsed model correctly produces a function with no `_block`
and that the resolution/codegen pipelines accept it for intrinsic functions.

### Phase 4: Verify annotation resolution in import context

**File**: `klang/src/model/tools/kdi_importer.cpp`

When the template source is re-parsed and built, the annotations
(`@annotations::Intrinsic(...)`) need to resolve against the `Intrinsic`
annotation type. This type is defined in `libk/libk/src/annotations.k` which
is part of module `k`.

Since the compiler auto-injects `import k;` for all modules except `k` itself,
the consumer should already have access to the annotations namespace.

**Risk**: The re-parse happens during `kdi_importer::materialise_template_def`,
which runs BEFORE the full resolution passes. At that point, the `Intrinsic`
annotation type might not yet be materialised from k.kdi.

**Fix** (if needed): Ensure that `k.kdi` is loaded and its annotations namespace
is materialised before re-parsing template definitions from other KDIs.

### Phase 5: Integration test

**File**: `klang/tests/test-import.cpp`

Add test case:
```cpp
TEST_CASE("cross-module template — intrinsic UniSlot consumer instantiation",
          "[import][e2e][template][cross-tpl][intrinsic]") {
    auto result = build_exec_with_lib(
        // Library defines UniSlot-like template with @Intrinsic methods
        R"K(
            module intrlib;
            namespace annotations {
                annotation Intrinsic { name : const char[]; }
            }
            template<typename T>
            struct Slot {
                private:
                _slot : T;
                public:
                @annotations::Intrinsic("UniSlot::constructor")
                Slot();
                @annotations::Intrinsic("UniSlot::destructor")
                ~Slot();
                @annotations::Intrinsic("UniSlot::construct")
                construct();
                @annotations::Intrinsic("UniSlot::destruct")
                destruct();
                get() : T& { return _slot; }
            }
            // Force at least one instantiation in the lib for linking
            lib_test() : int {
                s : Slot<int>;
                s.construct();
                s.get() = 77;
                result : int = s.get();
                s.destruct();
                return result;
            }
        )K",
        // Consumer instantiates with its own type
        R"K(
            module intrexec;
            import intrlib;
            struct Widget {
                v : int;
                Widget() { v = 42; }
            }
            main() : int {
                s : Slot<Widget>;
                s.construct();
                result : int = s.get().v;
                s.destruct();
                return result;
            }
        )K");
    REQUIRE( result.exit_code == 42 );
}
```

### Phase 6: Test with the real stdlib (libk)

Once Phases 1–5 pass, attempt:
```k
module myapp;
// import k; is auto-injected

main() : int {
    slot : UniSlot<int>;
    slot.construct();
    slot.get() = 100;
    result : int = slot.get();
    slot.destruct();
    return result;
}
```

This exercises the full path: libk.kdi → re-parse UniSlot → instantiate → intrinsic codegen.

## Notes

- The `source_text` path (raw parser capture) is the **primary** mechanism.
  The `k_source_emitter` is only a **fallback** when `source_text` is empty.
  If Step 0 shows that `source_text` is correctly captured and contains all
  annotations + member templates, then Phases 1–3 (emitter work) can be
  **deferred** since the raw text is used preferentially.

- The key questions are really:
  1. Is `source_text` captured correctly for UniSlot with its new member template?
  2. Does the re-parse + model-build succeed in the consumer context?
  3. Does `get_intrinsic_name()` fire on the re-built instantiation?

  Start with Step 0 and the integration test — the answer may reveal that less
  code is needed than anticipated.
